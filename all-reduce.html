How the model is actually split — 3D parallelism

A 70B+ model doesn't fit (or run fast enough) on one GPU, so frontier labs combine three kinds of parallelism. Gradient all-reduce — this page's topic — happens across the data-parallel dimension.

Data parallel

Same model, different data

Each replica trains on its own data shard, then all-reduces gradients every step so all replicas stay identical. This is the traffic we visualize below.

Tensor parallel

One layer, split across 8 GPUs

Each matrix multiply is sliced across the 8 GPUs inside a node — needs an all-reduce inside every layer, so it must stay on NVLink.

Pipeline parallel

Layers split into stages

Groups of layers live on different nodes; micro-batches flow through like an assembly line. Only thin activations cross stage boundaries.

Example layout for 8,192 GPUs: tensor parallel = 8 (inside each node) × pipeline parallel = 16 → one model copy spans 128 GPUs → data parallel = 64 replicas. The gradient all-reduce then runs across those 64 replicas, and each GPU only syncs its 1/128 slice of the model — much smaller than the full 140 GB.

2One training step — yes, gradients sync every step

Each step: forward (compute loss) → backward (compute gradients) → all-reduce (average gradients across all replicas) → optimizer (update weights). The trick: gradients for the last layers are ready first during backward, so communication starts immediately and runs concurrently with the rest of backward. Toggle overlap and press play.

3Ring all-reduce — the basic algorithm GPUs use to build a sum

4 GPUs split the gradient into 4 chunks (A–D) and pass them around a ring. 3 reduce-scatter steps + 3 all-gather steps and everyone holds the full sum. Per-GPU traffic ≈ 2 × gradient size, independent of GPU count.

5Tree all-reduce — the structure that connects nodes

16-node example (real clusters: 1,024+). Leaves = the gradient chunk each node holds. Pairs sum upward (reduce); once the root holds the global sum it flows back down (broadcast). A ring needs hops proportional to node count, but a tree finishes in log₂(N) levels.

Inner vertices are not separate machines — one of the two children simply holds the partial sum on behalf of the pair. In practice NCCL runs two complementary trees at once (double binary tree) so no link sits idle.

7Putting numbers on it — how long is one step, really?

Worked example: 70B-class model, 8,192 H100s (1,024 nodes), ~4M tokens per global batch, 3D parallelism (TP 8 · PP 16 · DP 64).

Scaling up — a 175B (GPT-3-class) model

Compute per step ≈ 6 × params × batch tokens = 6 × 175B × 4M ≈ 4.2×10¹⁸ FLOPs. Iteration time barely changes with model size — labs just scale the cluster to keep it in the same 1–5 s band.

Modern run (8,192 H100s)≈ 1.5–2 s per iteration — gradient is 350 GB, but only ~2.7 GB per GPU after TP×PP sharding, so the all-reduce is ~0.1–0.3 s and hidden by overlap. ~500k steps over 2T tokens ≈ 10–12 days of pure step time.
Original GPT-3 (2020, ~10,000 V100s)≈ 13 s per iteration at ~20% MFU with a 3.2M-token batch — ~94k steps over 300B tokens ≈ a month. Same model class, ~8× slower per step than today's hardware (V100 → H100, 100 → 400 Gb/s NICs).

So the answers to the two big questions: (1) Yes — gradients are synchronized on every single optimizer step; skip it and the replicas drift apart into different models. (2) The all-reduce itself takes tens to hundreds of milliseconds at frontier scale, and because it overlaps with backward compute, the visible cost is close to zero on a healthy network. That's why labs obsess over fabric reliability: one slow link (a "straggler") stalls all 8,192 GPUs at the synchronization barrier every step.

8Speed intuition — "but copying 100 GB takes seconds!"

Fair instinct — through one link, it does. Every answer below comes down to a single principle: no link ever carries the whole gradient, and every link in the datacenter works at the same time.

How long does moving 100 GB actually take?

NVMe SSD~7 GB/s → ~14 s

PCIe Gen5 x16~64 GB/s → ~1.6 s
One node's 8 NICs combined400 GB/s → 0.25 s
NVLink/NVSwitch (intra-node)~900 GB/s → ~0.11 s

The sync pipeline is engineered precisely to dodge the "2 s per NIC" reality: shrink what each NIC carries, push the bulk over NVLink (18× faster), and hide the rest behind backward compute.

If one NIC needs ~2 s for 100 GB, how is the whole all-reduce sub-second?
Because the 140 GB never goes through one pipe.
  1. All-reduce isn't "everyone sends everything to everyone." With ring/tree algorithms, each byte crosses each link about twice in total — once being reduced, once being broadcast back.
  2. The gradient is split 8 ways before touching the network. After the NVLink reduce-scatter, each GPU holds only 17.5 GB (140 ÷ 8) and all-reduces it through its own NIC — 8 NICs per node streaming in parallel ⇒ 400 GB/s per node.
  3. Every node does this simultaneously. 8,192 NICs together move ~410 TB/s. Per-GPU cost ≈ 2 × 17.5 GB ÷ 50 GB/s = 0.7 s — regardless of node count.
  4. With 3D parallelism it's smaller still: each GPU owns ~1–3 GB, so the all-reduce drops to tens of milliseconds.
The tree merges pairs level by level — isn't that one-by-one?

Within a level: fully parallel — node1+node2 → node12 and node3+node4 → node34 happen at the same instant on different links (512 simultaneous merges at the first level of a 1,024-node tree). Across levels: yes, there's a dependency chain — node12+node34 must wait for both inputs — but the chain is only as long as the tree is tall: log₂(1024) = 10 levels. So 1,023 merges of work finish in 10 steps of time.

Chunk pipelining hides even those 10 levels. The data streams as many small chunks: while level 2 sums chunk #1, level 1 is summing chunk #2 and the leaves are sending chunk #3. Once the pipeline fills (10 hops × microseconds), every level is busy simultaneously — tree height costs only a tiny latency term, not bandwidth.

The final sum must reach all 1,024 nodes — doesn't that cost 1,024 × copy time?

No — every node that receives the result immediately becomes a sender too. Coverage doubles each hop: 1 → 2 → 4 → 8 → … → 1,024 in just 10 hops. The total work is still N−1 = 1,023 copies, but it's spread across 1,023 different links running in parallel, and with chunk pipelining the wall-clock converges to ≈ the time to copy the data once (17.5 GB ÷ 50 GB/s ≈ 0.35 s) — whether there are 16 nodes or 16,000.

"N × copy time" is real in exactly one design: the old parameter-server star, where one server pushes the result to N workers through its single uplink. That's the red "naive: send to all" bar in the calculator above — and it's precisely what all-reduce replaced. Watch it live in section 5: during broadcast (steps 5–8), the active amber links go 1 → 2 → 4 → 8.

So… everything runs in parallel?
Yes — parallelism is stacked at every layer:
  1. Within a tree level — all pair-merges fire simultaneously on different links.
  2. Across levels — chunk streaming pipelines them; every level works on a different chunk at once.
  3. Across the 8 gradient slices — each NIC runs its own independent tree, concurrently.
  4. Across all nodes — every node participates in every phase at the same time; nobody waits a turn.
  5. Against compute — the whole all-reduce runs while the GPUs are still doing backward (network engines and compute units are separate hardware).
The only genuinely serial residue: the ~10-hop pipeline fill-up (microseconds) and the final gradient bucket the optimizer must wait for — the small exposed tail in the section 2 timeline. The right mental model isn't "data moving around a cluster"; it's every link in the datacenter firing at once, each carrying a different small piece.

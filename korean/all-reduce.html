All-Reduce·시각화

초대규모 분산 학습에서 그래디언트가 동기화되는 방식

1프런티어 학습 클러스터의 구조

노드 하나에는 NVSwitch(~900 GB/s 전대전)로 연결된 GPU 8개와 NIC 8개가 들어갑니다 — GPU당 400 Gb/s NIC 하나, “레일 최적화(rail-optimized)” 구성. 수천 개의 노드가 leaf/spine 구조의 InfiniBand 또는 RoCE 패브릭에 매달립니다. 클러스터 규모 슬라이더를 움직여 스케일을 체감해 보세요.

모델은 실제로 어떻게 쪼개지는가 — 3D 병렬화

70B 이상의 모델은 GPU 하나에 들어가지 않(거나 충분히 빠르게 돌지 않)기 때문에, 프런티어 연구소들은 세 가지 병렬화를 조합합니다. 이 페이지의 주제인 그래디언트 all-reduce는 데이터 병렬 차원에서 일어납니다.

데이터 병렬

같은 모델, 다른 데이터

각 복제본이 자기 데이터 샤드로 학습한 뒤, 매 스텝 그래디언트를 all-reduce해서 모든 복제본을 동일하게 유지합니다. 아래에서 시각화하는 트래픽이 바로 이것입니다.

텐서 병렬

한 레이어를 GPU 8개에 분할

각 행렬 곱이 노드 내부의 GPU 8개에 걸쳐 쪼개집니다 — 레이어마다 all-reduce가 필요하므로 NVLink 위에 머물러야 합니다.

파이프라인 병렬

레이어를 스테이지로 분할

레이어 묶음이 서로 다른 노드에 놓이고, 마이크로배치가 조립 라인처럼 흘러갑니다. 스테이지 경계를 넘는 것은 얇은 activation뿐입니다.

8,192 GPU의 예시 배치: 텐서 병렬 = 8 (노드 내부) × 파이프라인 병렬 = 16 → 모델 사본 하나가 GPU 128개에 걸침 → 데이터 병렬 = 복제본 64개. 그래디언트 all-reduce는 이 64개 복제본 사이에서 돌고, 각 GPU는 모델의 1/128 조각만 동기화합니다 — 전체 140 GB보다 훨씬 작습니다.

2학습 한 스텝 — 네, 그래디언트는 매 스텝 동기화됩니다

각 스텝: forward (손실 계산) → backward (그래디언트 계산) → all-reduce (모든 복제본의 그래디언트 평균) → optimizer (가중치 업데이트). 비결: backward 중에 마지막 레이어들의 그래디언트가 가장 먼저 준비되므로, 통신이 즉시 시작되어 나머지 backward와 동시에 진행됩니다. 중첩(overlap)을 토글하고 재생을 눌러 보세요.

70B급 학습을 보여주는 예시 수치입니다. 중첩을 켜면 all-reduce가 버킷(각 ≈25–100 MB)으로 잘게 나뉩니다: backward가 마지막 레이어들의 그래디언트를 끝내는 즉시 해당 버킷이 네트워크를 날기 시작하고, 그동안 앞쪽 레이어들은 아직 계산 중입니다. backward가 끝난 뒤에는 통신의 작은 꼬리만 드러납니다.

3링 all-reduce — GPU들이 합을 만드는 기본 알고리즘

GPU 4개가 그래디언트를 4개 청크(A–D)로 나눠 링을 따라 전달합니다. reduce-scatter 3단계 + all-gather 3단계면 모두가 전체 합을 갖게 됩니다. GPU당 트래픽 ≈ 그래디언트 크기의 2배, GPU 수와 무관합니다.

시작 단계 0 / 6

링 방향: GPU 0 → 1 → 2 → 3 → 다시 0. 채워진 사각형 = 그 청크에 합산된 GPU 기여 수. 주황 테두리 = 이번 단계에 받은 청크.

4계층형 3단계 — 수천 노드에서 실제로 일어나는 일

예시: 1,024 노드 × 8 GPU = 8,192 GPU, 70B 모델 (그래디언트 140 GB). 그림은 1,024개 노드 중 2개, 노드당 8개 GPU 중 4개만 보여줍니다.

시작 단계 0 / 3

자기 그래디언트만 노드 내부 합 (GPU 8개) 전역 합 (8,192 GPU)
⇄

각 GPU의 사각형 4개 = 그래디언트 청크 A–D. 2단계에서는 같은 청크를 담당하는 GPU들(노드 0의 GPU k ↔ 노드 1의 GPU k ↔ …)이 노드 경계를 넘어 합산합니다.

5트리 all-reduce — 노드들을 잇는 구조

16노드 예시 (실제 클러스터: 1,024개 이상). 잎(leaf) = 각 노드가 들고 있는 그래디언트 청크. 쌍끼리 위로 합산하고(reduce), 루트가 전역 합을 가지면 다시 아래로 흘려보냅니다(broadcast). 링은 노드 수에 비례하는 홉이 필요하지만, 트리는 log₂(N) 레벨이면 끝납니다.

시작 단계 0 / 8

대기 (자기 청크만) 부분합 (숫자 = 합쳐진 노드 수) 전역 합 (16/16)

내부 정점은 별도의 머신이 아닙니다 — 두 자식 중 하나가 그 쌍을 대표해 부분합을 들고 있을 뿐입니다. 실전에서 NCCL은 상호 보완적인 트리 두 개를 동시에 돌려서(이중 이진 트리, double binary tree) 어떤 링크도 놀지 않게 합니다.

7숫자로 따져보기 — 한 스텝은 실제로 얼마나 걸릴까?

계산 예시: 70B급 모델, H100 8,192개 (1,024 노드), 글로벌 배치당 약 4M 토큰, 3D 병렬화 (TP 8 · PP 16 · DP 64).

스텝당 연산량≈ 6 × 70B 파라미터 × 4M 토큰 ≈ 1.7×10¹⁸ FLOPs → H100 8,192개에서 MFU ~40–50% 기준 ≈ 0.5–1.5초
GPU당 동기화할 그래디언트140 GB ÷ 128 (TP×PP 샤드) ≈ GPU당 1.1 GB, DP 복제본 64개 사이에서 all-reduce
순수 all-reduce 시간~2 × 1.1 GB를 400 Gb/s(50 GB/s)로 전송 + 트리 지연 ≈ 50–300 ms
중첩 후 드러나는 시간버킷들이 backward 중에 날아감 → 보통 ≈ 0–100 ms만 보임
총 스텝 시간≈ 1–2초 → 몇 주간의 학습 동안 수만 스텝

규모 키우기 — 175B (GPT-3급) 모델

스텝당 연산량 ≈ 6 × 파라미터 × 배치 토큰 = 6 × 175B × 4M ≈ 4.2×10¹⁸ FLOPs. 반복(iteration) 시간은 모델이 커져도 거의 변하지 않습니다 — 연구소들은 클러스터를 키워서 같은 1–5초 대역을 유지합니다.

최신 학습 (H100 8,192개)≈ 반복당 1.5–2초 — 그래디언트는 350 GB지만 TP×PP 샤딩 후 GPU당 ~2.7 GB뿐이라 all-reduce는 ~0.1–0.3초이고 중첩에 가려집니다. 2T 토큰에 ~50만 스텝 ≈ 순수 스텝 시간만 10–12일.
오리지널 GPT-3 (2020, V100 ~10,000개)≈ 반복당 13초 — MFU ~20%, 3.2M 토큰 배치 — 300B 토큰에 ~9.4만 스텝 ≈ 약 한 달. 같은 모델급인데 오늘날 하드웨어보다 스텝당 ~8배 느림 (V100 → H100, 100 → 400 Gb/s NIC).

그래서 두 가지 큰 질문의 답은: (1) 네 — 그래디언트는 매 optimizer 스텝마다 동기화됩니다; 건너뛰면 복제본들이 서로 다른 모델로 갈라집니다. (2) all-reduce 자체는 프런티어 규모에서 수십~수백 밀리초가 걸리고, backward 연산과 중첩되기 때문에 건강한 네트워크에서는 눈에 보이는 비용이 거의 0입니다. 연구소들이 패브릭 신뢰성에 집착하는 이유죠: 느린 링크 하나(“스트래글러”)가 매 스텝 동기화 장벽에서 8,192개 GPU 전체를 멈춰 세웁니다.

8속도 직관 — “근데 100 GB 복사는 몇 초나 걸리잖아요!”

타당한 직관입니다 — 링크 하나를 거치면 정말 그렇습니다. 아래 모든 답은 한 가지 원칙으로 귀결됩니다: 어떤 링크도 그래디언트 전체를 나르지 않고, 데이터센터의 모든 링크가 동시에 일합니다.

동기화 파이프라인은 “NIC당 2초”라는 현실을 피하도록 정밀하게 설계되어 있습니다: 각 NIC이 나르는 양을 줄이고, 큰 덩어리는 NVLink(18배 빠름)로 처리하고, 나머지는 backward 연산 뒤에 숨깁니다.

NIC 하나로 100 GB에 ~2초가 걸린다면, 어떻게 전체 all-reduce가 1초 미만인가요?
140 GB가 결코 파이프 하나를 통과하지 않기 때문입니다.
  1. All-reduce는 “모두가 모두에게 전부 보내기”가 아닙니다. 링/트리 알고리즘에서는 각 바이트가 각 링크를 총 두 번 정도만 지납니다 — 한 번은 합산(reduce)되며, 한 번은 다시 broadcast되며.
  2. 그래디언트는 네트워크에 닿기 전에 8등분됩니다. NVLink reduce-scatter 후 각 GPU는 17.5 GB(140 ÷ 8)만 들고 자기 NIC으로 all-reduce합니다 — 노드당 NIC 8개가 병렬로 스트리밍 ⇒ 노드당 400 GB/s.
  3. 모든 노드가 이걸 동시에 합니다. 8,192개 NIC이 합쳐서 ~410 TB/s를 옮깁니다. GPU당 비용 ≈ 2 × 17.5 GB ÷ 50 GB/s = 0.7초 — 노드 수와 무관합니다.
  4. 3D 병렬화까지 적용하면 더 작아집니다: GPU당 ~1–3 GB만 담당하므로 all-reduce는 수십 밀리초로 떨어집니다.
트리는 레벨별로 쌍을 합치는데 — 그거 하나씩 차례대로 아닌가요?

한 레벨 안에서는: 완전 병렬 — node1+node2 → node12와 node3+node4 → node34가 서로 다른 링크에서 같은 순간에 일어납니다 (1,024노드 트리의 첫 레벨에서는 512개의 병합이 동시 진행). 레벨 사이에는: 맞습니다, 의존 사슬이 있습니다 — node12+node34는 두 입력을 기다려야 하죠 — 하지만 그 사슬의 길이는 트리의 높이만큼입니다: log₂(1024) = 10 레벨. 그래서 1,023번의 병합이라는 작업이 10단계의 시간에 끝납니다.

청크 파이프라이닝은 그 10레벨마저 숨깁니다. 데이터는 작은 청크 여러 개로 흐릅니다: 레벨 2가 청크 #1을 합산하는 동안 레벨 1은 청크 #2를 합산하고, 잎들은 청크 #3을 보냅니다. 파이프라인이 한 번 차고 나면(10홉 × 마이크로초) 모든 레벨이 동시에 바쁩니다 — 트리 높이는 아주 작은 지연 항으로만 남고, 대역폭은 잃지 않습니다.

최종 합이 1,024개 노드 전부에 도달해야 하는데 — 1,024 × 복사 시간이 들지 않나요?

아니요 — 결과를 받은 노드는 즉시 송신자가 됩니다. 커버리지가 홉마다 2배가 됩니다: 1 → 2 → 4 → 8 → … → 1,024, 단 10홉. 총 작업량은 여전히 N−1 = 1,023회 복사지만, 그것이 1,023개의 서로 다른 링크에 병렬로 분산되고, 청크 파이프라이닝 덕분에 벽시계 시간은 데이터를 한 번 복사하는 시간(17.5 GB ÷ 50 GB/s ≈ 0.35초)으로 수렴합니다 — 노드가 16개든 16,000개든.

“N × 복사 시간”이 실제로 맞는 설계는 딱 하나: 옛날의 파라미터 서버 스타 구조로, 서버 하나가 단일 업링크를 통해 N개 워커에게 결과를 밀어 넣습니다. 위 계산기의 빨간 “단순 방식: 모두에게 전송” 막대가 바로 그것이고, all-reduce가 대체한 것이 정확히 그 방식입니다. 5번 섹션에서 실시간으로 확인하세요: broadcast(5–8단계) 동안 활성화된 주황 링크가 1 → 2 → 4 → 8로 늘어납니다.

그러니까… 전부 병렬로 돈다는 건가요?
네 — 병렬성이 모든 층위에 겹겹이 쌓여 있습니다:
  1. 트리 레벨 안에서 — 모든 쌍-병합이 서로 다른 링크에서 동시에 발화합니다.
  2. 레벨 사이에서 — 청크 스트리밍이 레벨들을 파이프라인화합니다; 모든 레벨이 동시에 서로 다른 청크를 처리합니다.
  3. 8개 그래디언트 조각 사이에서 — 각 NIC이 독립적인 트리를 동시에 운영합니다.
  4. 모든 노드에 걸쳐 — 모든 노드가 모든 단계에 동시에 참여합니다; 누구도 차례를 기다리지 않습니다.
  5. 연산과 맞물려 — GPU가 아직 backward를 도는 동안 all-reduce 전체가 진행됩니다 (네트워크 엔진과 연산 유닛은 별개의 하드웨어).
정말로 직렬로 남는 것은: ~10홉짜리 파이프라인 채우기(마이크로초)와 optimizer가 기다려야 하는 마지막 그래디언트 버킷 — 2번 섹션 타임라인의 작은 노출 꼬리 — 뿐입니다. 올바른 멘탈 모델은 “데이터가 클러스터를 돌아다닌다”가 아니라, 데이터센터의 모든 링크가 각자 다른 작은 조각을 들고 일제히 발화하는 그림입니다.
